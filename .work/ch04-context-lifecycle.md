# 第 4 章 上下文的六个动作

> 上下文不是越大越好，是越干净越好。查用量、主动压、落盘交接，三步管住它。

## 为什么需要它

同一个会话跑两个小时，会出这种事：

第 20 轮你决定"这次不改数据库"，第 45 轮它又给你加了一个字段，还理直气壮地说"按之前的方案需要这个字段"。

它没说谎。**"之前的方案"确实在它的上下文里**——只不过是你二十轮前就否掉的那个。上下文不会自己过期，被否掉的假设和当前的决定躺在一起，权重还差不多。

这就是上下文腐烂：信息还在，但已经不代表现在的事实。

## 术语表

| 术语 | 人话 | 类比 |
| --- | --- | --- |
| 上下文窗口 | 这次会话它能看到的全部内容 | 桌面能摊开的纸 |
| 上下文腐烂 | 旧假设混在当前决定里 | 桌上还摊着作废的图纸 |
| 交接文件 | 把状态写进文件，供下一轮读 | 交班记录 |

## 第一步：先看用量

不知道用了多少，就谈不上管理。两个常用命令：

| 工具 | 命令 | 看什么 |
| --- | --- | --- |
| Claude Code | `/context` | 当前上下文占了多大比例、被什么占的 |
| Codex | `/status` | 同样的用量信息 |

习惯是**每做完一个功能看一眼**。超过一半就该考虑压缩，而不是等它自己报错。

## 六个动作

一轮工作做完，你有六个选择。它们解决的是不同问题，别只会用第一个：

| 动作 | 做什么 | 什么时候用 |
| --- | --- | --- |
| 继续 `/continue` | 原地接着干，什么都不清 | 任务没完、方向确定、上下文仍准确 |
| 回滚 `/rewind` | 退到某一轮重新开始，清掉之后的内容 | 最近几步走歪了，但前面的判断还有效 |
| 压缩 `/compact` | 保留要点，丢掉过程细节 | 会话变长但任务还要继续 |
| 清空 `/clear` | 全新会话，什么都不带 | 换一个不相关的任务 |
| 分支 `/branch` | 带着当前上下文去开一个新任务 | 主线正确，但要试一条岔路 |
| 子代理 subagent | 独立上下文，只把结果带回主会话 | 一件事可以整个外包出去 |

大部分人的默认动作只有一个：**继续**。然后在一个越来越脏的会话里越干越乱，最后归因为"模型不太行"。

## 压缩的三条操作建议

压缩是收益最高、也最容易用错的动作。

**一、手动压，并且关掉自动压缩。** 自动压缩通常发生在快满的时候，那时上下文已经脏了很久，压出来的是脏东西的摘要。所以主动压，并把 autocompact 关掉，把时机握在自己手里。

**二、压缩要给方向。** 一句"压缩一下"它只能自己猜重要性。给方向才准：

```text
压缩上下文，保留：
- 已经确定的方案（JWT 放 header，不放 cookie）
- 还没做完的三件事
- 踩过的坑（Redis key 格式不能改）
不要保留：中间试错的几版代码、被否掉的方案
```

**三、压缩前先落盘。** 这是最有价值的一条。在压之前，先让它写交接文件：

```text
把当前的进展、待办事项、已知的坑写进 HANDOFF.md。
要求：我明天开一个全新的会话，只读这个文件就能直接继续工作，不用问你任何问题。
```

写完 `HANDOFF.md`，你就可以放心 `/clear`。新会话第一句：

```text
读一下 HANDOFF.md 文件，我要继续工作。
```

断开上下文和不断开，效果一样——因为状态在文件里，不在会话里。

## HANDOFF.md 长什么样

关键是**具体到能直接开工**，不是写周报：

```markdown
# 认证重构 - 交接

## 已完成
- JWT 签发逻辑迁移到 auth/jwt.service.ts
- 登录接口已切到新逻辑，测试通过

## 待办
- refresh token 还没迁移，逻辑在 auth/legacy.ts:120
- bar.ts 有个 unused import 的 warning，顺手修

## 已知的坑
- 别动 auth/session.ts 的 Redis key 格式，线上有老数据依赖
- 方案 A（中间件里验签）试过，不行：中间件拿不到 user context
```

"已知的坑"这段最值钱。它记录的是一条**已经证伪的路径**——没有它，新会话里的模型会兴高采烈地再走一遍。

## 翻车现场

::: warning 一个会话干完四件事
上午在一个会话里改登录、改缓存、修样式，都很顺。下午第四件事——改权限——它开始胡来：把已经废弃的旧接口又调回来。

原因很简单：前三个任务的上下文全在，里面有一堆"旧的怎么写"的代码片段。它分不清哪个是"现在的写法"。
:::

## 一条经验规则

- **换任务就 `/clear`**。不相关的事不要挤在一个会话里。
- **一个任务超过二三十轮就 `/compact`**，别等它开始记错。
- **要开岔路就用 `/branch` 或 subagent**，别把主线的会话搞乱。
- **每次 `/compact` 或 `/clear` 之前，先写 `HANDOFF.md`**。

## 自测三问

1. 你现在的默认动作是哪个？有没有一种情况，你其实该 `/clear`，却一直"继续"下去了？
2. 为什么"压缩前先写交接文件"比"直接压缩"更可靠？
3. `HANDOFF.md` 里如果只能留一段，留哪段？为什么？
