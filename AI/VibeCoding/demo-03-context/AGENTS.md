# Context Engineering：项目记忆与交接规则

这个项目使用文档保存项目记忆。聊天记录会消失或被截断；产品方案、技术约束、已确认决定和当前进度必须保存在仓库中。

## 每次对话的起点

在回应用户、提出方案、修改代码或运行验证之前，必须按顺序阅读：

1. `docs/product.md`：要解决的问题、范围和验收标准。
2. `docs/architecture.md`：技术边界、结构和实现约束。
3. `docs/decisions.md`：已确认且不能被无意推翻的决定。
4. `docs/handoff.md`：上一轮工作的状态、风险和下一步。

如果这是新会话或接手工作，先用简短中文说明：你理解的当前项目状态、未决问题和下一步；然后再继续。

## 文档更新规则

- 收到新的产品想法、需求变更或验收要求时，先更新 `docs/product.md`，再讨论或实施。
- 出现技术取舍、范围取舍或有多个合理实现方式时，将用户确认的结论记录到 `docs/decisions.md`；每条记录必须写清决定、原因、备选方案和影响范围。
- 当技术栈、项目结构、数据模型、关键约束或运行方式发生变化时，更新 `docs/architecture.md`。
- 不得把关键决定只留在对话中，也不得在后续工作中悄悄推翻已记录的决定。

## 实施前与实施后

- 实施前：确认 `docs/handoff.md` 的当前状态与 `docs/product.md` 的验收目标一致；若不一致，先询问用户或更新文档。
- 实施中：遵守产品、架构和决策文档；发现冲突时暂停并说明冲突。
- 每次讨论、设计、实现、修复或验证结束时：更新 `docs/handoff.md`。这是一项必做的交接动作，不等待用户提醒。

## 交接记录必须包含

- 本次目标与当前阶段。
- 已完成内容和涉及文件。
- 已执行的验证及结果。
- 未决问题、风险或阻塞。
- 明确的下一步建议。
- 下次开始前必须阅读或确认的内容。

交接记录的最新条目放在最顶部；不要覆盖历史记录。
