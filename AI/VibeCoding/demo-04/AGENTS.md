# SDD 工作流：从一句项目想法到可验收实现

此项目采用 Spec-Driven Development（SDD）。用户可能只会描述一个项目想法；你的职责是将想法转化为可审阅、可追踪、可验证的交付过程，而不是立刻写代码。

## 最高优先级：固定工作流

每次收到新项目需求时，严格按以下顺序工作。除非用户明确要求跳过某一步，否则不可跳步，也不可在 Implement 之前创建业务代码。

1. **Specify**：阅读 `docs/workflow.md` 与 `spec/README.md`；创建或更新 `spec/requirements.md`。
2. **Clarify**：提出关键澄清问题，等待用户回答；将结论补充进 `spec/requirements.md`。
3. **Plan**：创建 `spec/plan.md`，说明架构、文件职责、数据与交互流程、验证策略。
4. **Tasks**：创建 `spec/tasks.md`，拆为按依赖顺序排列、可验证的小任务。
5. **Implement**：仅在用户确认规格、计划和任务后实施；同步勾选已验证的任务。
6. **Converge**：创建 `spec/convergence-report.md`，逐条验收、修复偏差、重新验证，直至实现向规格收敛。

## 阶段门禁

- Specify 结束：总结规格并请求确认，停止。
- Clarify 结束：问题未得到回答前，不猜测关键产品决策。
- Plan 结束：总结计划并请求确认，停止。
- Tasks 结束：展示任务清单并请求确认，停止。
- Implement：如发现规格冲突或缺失，回到 Clarify；不得悄悄自行决定。
- Converge：不得因为实现困难而降低或改写验收标准；应修复、说明阻塞，或请求产品决策。

## 文档与沟通要求

- `spec/requirements.md` 是需求真相来源；实现以它为准。
- 所有关键决定都应写进规格，而不只存在于聊天记录。
- 每次回复都说明：当前阶段、已更新文件、下一步需要用户做什么。
- 面向非技术用户解释时使用清晰中文；技术细节保留在相应文档中。

## 默认技术边界（仅在用户未另行指定时适用）

- 优先选择最小、可直接运行的方案。
- 不引入第三方依赖、后端、账户或外部服务，除非规格明确要求并获用户确认。
- 在 Implement 阶段才决定具体技术文件；不得预先生成业务代码。
