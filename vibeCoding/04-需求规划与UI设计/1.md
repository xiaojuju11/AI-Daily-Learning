# SDD -- Spec-Driven Development  规格驱动开发

 - spec-kit  一套心法：核心就是将那套问答、那套流程固化成工具和skill


# Plan Mode
 - 计划模式，非常好用，不用自己拆任务了

 - 但是，很多人都用错了它：
  1. 甩手掌柜
  2. 劳模型

 ## SDD为什么火
  先把需求写成结构化的规则（spec），再从spec中提取出任务（plan），最后让Agent根据plan来开发。

  - spec 回答 “做什么”
  - plan 回答 “怎么做”  （tickets 工单）

  * SDD 强迫你把想法落成文档，再让文档驱动开发


 ## SDD 的坑
  spec 和 plan 的本质是把执行步骤拆清楚，但是它不该替你做决策。 但是，很多人用错了它，很多人是让AI在信息不充分的情况下直接生成 spec ———— 这就等于让AI把关键决策全做了。


  - 最适合批量开发同类型的项目


 ## 解药：把决策和规划分开
    传统方式是把两件事混在一起：AI一边做决策，一边执行步骤。正确的做法是：
     1. 先通过AI把关键决策敲定
     2. 在让AI基于已经去定的决策，来生成 plan

    （就像盖房子：你不会让施工团队一遍画图纸，一边砌墙。应该跟建筑师先谈论好布局、材料、风格、图纸等，再让施工团队根据图纸来砌墙。）

   - 落到实操上，就是把 “直接开 plan mode” 换成一套讨论先行的流程，在这套流程中，我们可以：
     1. 让AI先摸底 （prompt: 先别出方案，把跟xxx功能项目代码读一遍，告诉我：现在是怎么实现的？如果要加xx功能，你觉得会牵扯到哪些地方？）

     2. 让AI来抬杠 （prompt: 我倾向于在现有的表上加xx字段，来实现xx功能，你觉得有什么问题？有没有我没考虑到的备选方案？不要顺着我说，先毛病）

     3. 全部都确认了，再让AI来生成 plan
