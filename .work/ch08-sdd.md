# 第 8 章 SDD：把决策和规划分开

> 规格驱动开发救不了"你根本没想清楚"，它的价值在于逼你把想法写下来——而决策必须由你做。

## 为什么需要它

一句话需求进去，三千行代码出来，方向全错。这类事故的根源不在执行，在**决策和执行被混在一起做了**。

传统做法是一边想一边写：边画图纸边砌墙。AI 时代这个错误被放大了，因为它砌墙太快，你来不及发现图纸是错的。

## 术语表

| 术语 | 人话 | 类比 |
| --- | --- | --- |
| SDD | 规格驱动开发：先写规格，再按规格拆任务 | 先出图纸，再排工序 |
| spec | 对"做成什么样"的结构化描述 | 建筑图纸 |
| plan | 从图纸拆出来的任务清单（工单） | 施工工序表 |
| Plan Mode | 让模型先出计划、不动手的模式 | 先开会再开工 |

## SDD 到底是什么

三步，顺序固定：

```text
1. 把需求写成结构化的规则  → spec（回答"做什么"）
2. 从 spec 里提取任务      → plan（回答"怎么做"）
3. 让 Agent 按 plan 开发
```

它的核心不是工具，是**强迫你把想法落成文档，再让文档驱动开发**。想法在脑子里时永远"差不多"，写下来才发现有三处没想清楚。

**Plan Mode 就是第 2 步的载体**：让它先输出计划、不动手。好处是不用自己拆任务——但很多人用错了它：

**甩手掌柜型。** 丢一句"帮我写个 spec"，拿着它生成的东西直接开工。

**劳模型。** 把 plan 写到最细的每一步，模型只负责打字，等于放弃了全部收益还多花一倍时间。

## 最危险的一步：让 AI 在信息不足时生成 spec

`spec` 和 `plan` 的本质是**把执行步骤拆清楚，它不该替你做决策**。

但如果你在信息不充分的情况下让它生成 spec——它只能自己补上缺的那部分：选哪张表、字段怎么加、状态怎么流转。**这等于让它把关键决策全做了。**

等你三天后发现表结构选错，改起来就是重建。

## 解药：先讨论，再规划

正确的顺序是三段，中间那段最容易被跳过。三段都可以直接复制：

### 一、先摸底

```text
先别出方案。把和"订单退款"相关的代码读一遍，然后告诉我：
1. 现在退款是怎么实现的？走哪个入口、写哪张表？
2. 如果要支持"部分退款"，会牵扯到哪些地方？
3. 有哪些地方我可能没意识到会被影响？
```

目的是把它把**你不知道自己不知道**的部分摊开。

### 二、让它抬杠

```text
我倾向于在 orders 表上加 refunded_amount 字段来实现部分退款。
你觉得有什么问题？有没有我没考虑到的备选方案？
不要顺着我说，先说毛病。
```

最后一句必须有。不加这句，你得到的是"这个方案很好，建议补充……"。

加了之后，你可能会听到："加字段之后历史订单的默认值怎么定？一笔订单多次部分退款，单字段存不下累计值。"——这类问题到写代码时才发现，返工成本是十倍。

### 三、确认完再生成计划

```text
上面确定的决策是：
- 用独立的 refunds 表，不用在 orders 上加字段
- 一次退款一条记录，支持多次部分退款
- 不支持跨订单合并退款

基于这些，生成一个 plan：拆成任务，标出每个任务动哪些文件、
依赖哪个任务、怎么验证。
```

差别就在一句：**决策是你给的，它只负责拆。** 这一句决定了 plan 是在落实你的判断，还是落实它自己的。

## 两个能省事的东西

- **spec-kit**：把上面这套"问答 + 流程"固化成工具和 skill，不用每次手动走一遍。核心心法就是那套提问顺序。
- **grill-me 类技能**：让 AI 反过来拷问你。你只说"我要做一个 xx 功能，你帮我梳理需求"，它会一轮轮追问，把你没想到的边界问出来。
- **superpowers 类插件**：你只有一个模糊想法时，它给你指方向、拆步骤。

工具会换，能力不变：**把"想清楚"这件事从你的脑内活动，变成一次有结构的对话。**

## 适用边界

SDD 最适合**批量开发同类型的项目**：一整套管理后台、一批相似的活动页、一组同构接口。spec 和 plan 能复用，第二次开始成本极低。

一次性小脚本、半天就扔的东西，写 spec 的时间比写代码长，不值得。

## 翻车现场

::: warning 三天后才发现表结构错了
需求是"用户可以收藏商品"。

一句"帮我写个 spec"，产出很漂亮：`favorites` 表，`user_id` + `product_id` + 时间戳。

三天后运营提要求："收藏要能分组。" 这时才发现：`user_id + product_id` 唯一，还是 `user_id + group_id + product_id` 唯一，决定了整张表要不要重建。

这个问题，在"先摸底 + 抬杠"那一步，问一句"以后会不会需要分组"就能提前暴露。
:::

## 自测三问

1. 你上一次让 AI 写计划，是"它拆你确认"，还是"它连方案一起定了"？
2. "先别出方案，先读代码"这句话，能避免哪一类返工？
3. 什么样的任务不值得写 spec？举一个你自己的例子。
