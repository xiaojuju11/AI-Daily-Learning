# 1.你平时是怎么用AI工具做项目开发的？
说白了就四件事：**教它规矩、把活说清楚、别让它越干越糊涂、让它自己验收。**

**一、先给它写个“入职说明”**

就是项目根目录那个说明文件。不用写太长，一两百行够了。只写它猜不到的事：怎么跑测试（写死命令，别写“注意效率”这种废话）、哪些文件绝对不能碰、当年为什么留了那段奇怪的代码。写太长反而坏事，它记不住，规则还互相打架。再挂个自动检查，它改完代码就自动查一遍，报错直接回传给模型让它自己改。

**二、派活别只说一句**

我得说清楚四件事：我要什么、哪里不能动、以前为什么这么写、做成什么样算完。特别是“算完”这条，你不说，它就会挑最容易达到的标准，然后告诉你“搞定了”。

稍大点的功能，我先让它读代码、告诉我它理解的现状，我纠正完，再听它提方案、挑毛病，关键几条我自己拍板，最后才让它写计划。不然它会替我做决定，还做得挺像那么回事。

**三、干久了它会变糊涂**

这不是模型降级，是聊太长了，前面一堆废信息挤着它。所以我差不多用到一半就让它写张“交接条”——干完啥、还差啥、哪里有坑——然后重开一轮。要翻一堆文件才能查明白的活，就扔一边让它自己干，只把结论拿回来。

**四、验收：能机器查的，我绝不自己看**

跑测试、跑检查，红了它自己修。做界面的，让它自己开浏览器看，还得故意造点极端情况：塞个超长名字、切暗色、把窗口缩到手机大小。反复踩过的坑，写成一条条大白话的测试，以后自动跑。

最后真正要我看的只有三样：这活到底该不该干、方向对不对、以及发出去就收不回来的操作——发版、发邮件、动数据库，这个确认键我不交给它。

一句话：我不是在打字催它写代码，我是在当包工头——派活、验收、把关。它干得不好，八成是我活没交代清楚。


# 2.平时开发有遇到什么问题吗？
遇到过，而且不少。挑几个印象最深的：

**一、它把我“看着没用”的东西删了**

最疼的一次：一段给老用户留的兼容逻辑，它判断成冗余代码，顺手删了。测试全绿，上线两天后老用户数据出问题。它不知道这段代码的来历——这个信息只在人脑子里。后来我把这段直接写进项目说明，标成禁区。

**二、绿灯骗人**

编译过了、测试过了、build 也过了，我打开浏览器一点：弹窗被底下那张表盖住一半。代码每一行都是对的，就是渲染出来不对。这让我明白一件事：机器只验它能看见的那一层，看不见的那层还得有人管。

**三、一个 bug 修五六轮，越修越歪**

回头看上下文，全是失败的尝试，它已经在错误的方向上跑出去很远了。现在我有个规矩：**改到第三轮还不对，先停下重开**，把已经确认的结论写下来，再在新会话里干。别在烂摊子上接着糊。

**四、它爱“改改试试”，不爱查根因**

表现出来就是来回打转、东改一处西改一处。这时候我会压住它：先别动手，说清楚你认为根因是什么、证据是什么。

**五、测试本身也会骗人**

AI 写的用例也会写错，红了不一定是页面坏了，可能是断言写歪了。所以每次红了我都得判断一句：这次是它错了，还是测试错了。

要说最要命的，其实不是它，是**我**。派活偷懒、验收走神、“看着差不多就过了”——我漏掉的每个坑，基本都能追到我自己少说了一句、少看了一眼。

还有一类到现在也没根治：**不吭声的失败**。它挂了不报警，我以为一切正常，等发现的时候已经停了十天。这种只能靠告警保底，但告警配多了又变成噪音，人就开始不看了。


# 3.你简历上的这个亲子教育项目，你说你是借助AI工具开发的，细说一下，你怎么一步一步把一个项目从0开始做上线的？

用 AI 做项目，我觉得中最重要的就是三个点：**把话说清楚、把检查交给机器、把踩过的坑变成资产。**写代码是这里面最不值钱的一环。

下面是我自己开发的一点心得

**一、我的活是管理，不是敲键盘。**

我不再是那个写代码的人，我是派活、给依据、验收、定方向的人。这件事想通了，很多纠结就没了：它写得快不等于我做得对，我派得糊，它就跑得偏，最后浪费的是我的时间。

**二、它永远自信，所以我不信"已完成"，我只信跑绿了的证据。**

它说"实现完成、可以直接使用"的时候，它并没有骗我，它就是个概率系统，压根没有"我不确定"这个表情。所以我不跟它争，我在外面包一层——产出拿出来，换个干净的上下文再审一遍，重要的地方换个模型再看一眼。让考生自己批卷子，分数永远是虚高的。

**三、它的记忆只有眼前这一段，所以它看到什么，由我决定。**

项目规矩、历史包袱、这次的边界，该给的给足，而且要给在它真正要用的那一刻，平时别塞。百科全书写进开机文档，等于什么都没写——它记不住，还会互相打架。会话也是一样，聊久了就变糊涂，不是你降智，是上下文脏了。

**四、能被机器判的，绝不用我的眼睛。**

类型错、风格错、逻辑错、构建挂，全是机器一秒钟能告诉你的，我为什么要花注意力去看？我的注意力只留给机器判不了的那部分：这活该不该干、这个方向对不对、这个界面难看不难看。

**五、同一个坑踩第二次，是我的问题。**

翻车不可怕，翻完不写下来才可怕。每翻一次车，我至少要产出一个东西：一条规则、一条清单、一个脚本。写规则的过程本身也在逼我想清楚——这个错的本质是什么、什么条件下会复现、边界定在哪不误伤。

**六、它不会怀疑自己，所以怀疑这一环只能我来补。**

这是我认为最值钱的一条。它可以比我快十倍、知道得比我多，但它写完一段代码心里不会发毛，我会。那种"这地方好像不太对"的感觉，就是我在这个协作里唯一不可替代的东西。

**现在拿这个项目举例子，我是做了一些操作**

补全后大概是这样——

**第一件事不是写代码，是写“做成什么样算完”。**

我先做的需求分析。需求文档不是让 AI 一口气生成的：主干我自己写，写清这个产品给谁用、解决什么问题、这一版只做什么；然后把主干交给 AI，让它挑三件事——我漏掉的场景、我写得含糊的地方、以及按现在的条件做起来很贵、甚至做不了的需求。

竞品分析我也交给它，但指令给具体：去 GitHub 按 star 找同类项目，**不要给我列功能清单**，我要的是“它为什么这么设计”——每个项目说清楚它解决的是用户什么场景下的问题、做了哪些取舍、砍了什么。我关心的是我可能没想到的那部分，比如它把某个功能做成“顺手就能用”，或者它专门防住了某种误操作。看完我只挑能补我盲区的采纳

这个产品就四个大功能：登录、拍照识图、每日一首古诗词、AI 问答。每个功能我都不写“做好一点”，而是写到能直接判定的程度：

- **登录**：token 过期要自动续上，用户不能被打断；同一屏五个请求同时过期，只能刷新一次，不能刷五次。
- **识图**：一张 3MB 的手机照片，十秒内出结果；失败能重试一次；传个 PDF 进去必须报错，不能白屏。
- **诗词**：同一天、换设备、清缓存，看到的必须是同一首；外部那个诗词接口挂了，要给昨天那首，不能空着。
- **问答**：答不出来就说不知道，不许编。

这些标准我会先让 AI 补一版——它很擅长把“正常流程”之外的边界情况列全：空数据、超长内容、断网、并发、超时，这些我自己想容易漏。但它补完我只当素材，最后哪条留、哪条砍、标准定到多严，是我一条一条拍板的。**因为标准定松了，它就会按最松的那个交活，然后跟我说“已完成”。**

所以这一步花的时间比写代码多得多，但值：后面每次派活，我把这份标准直接贴给它，它知道终点在哪，我也知道该验什么。

**第二件事，先搭一条最细的线。**

一个接口，一个页面，能把数据显示出来。这一步不为功能，为的是把跨域、请求封装、返回格式这些“通道”先确认一遍——通道不通，后面写多少功能都是白写。我最怕的不是写不出来，是功能写了三天，最后发现是跨域没配。

同时把规矩立起来：常用命令写成能直接复制执行的（`pnpm test xxx`，不是“注意测试效率”）、哪几个目录是禁区、后端地址走环境变量不许写死在代码里。每条“不许”后面我都跟一个“应该”，不然它遇到场景就卡住，或者自作主张另搞一套。

然后挂自动检查：改完文件自动跑类型和 lint，报错直接甩回给它自己修，不经过我。我的标准很土——**我故意写错一个类型，提交必须被拦下来。**拦不住，这套东西就是摆设。

**第三件事，先把接口定死。**

返回长什么样、字段叫什么、错误码怎么分，我先写好，前端先拿假数据把页面跑起来。不先定这个，它能给你三个接口三种返回格式，最后我在前端一个个对，纯属浪费。定死之后还有个好处：前后端能同时开工，我 review 只看“有没有按契约来”，不用猜它想干嘛。契约不许它偷偷加字段，要改先跟我说一声。

**然后才一个一个功能推，一个功能从页面推到数据库。**

推完一个、验完一个，不做“先把所有接口写完再写页面”那种——那种做法最后你会发现哪条线都不通。

顺序上我有讲究：**最不确定的先探。**识图依赖外部那个工作流，我会先拿二十张真照片去打它，量三个数：平均多久、最慢多久、错几次。如果最慢超过十五秒、或者十次错一次，那就不是写代码能救的，得先谈降级——加一次重试，还是干脆只出文字描述；实在扛不住，这个功能就砍。这种事越早发现越便宜，拖到最后一周就是灾难。

每个功能我都盯几个具体的点：

- **登录**：几个请求同时过期不能刷五次，得只刷一次，其余挂着等；刷新也失败就清干净，跳登录页。
- **识图**：图片先压到 1024 再传，要有超时、有重试、有 loading；后端要限流，一人一分钟最多三次，防刷。
- **诗词**：正确性不能靠定时任务撑着——缓存 key 里带日期，读的时候拼当天日期，没有就去拉，定时任务只负责提前热一下。这样服务重启、任务挂了，用户也不会看到昨天的诗。锁用 SETNX，值用随机串，删之前先校验，而且必须放 finally。
- **问答**：答不出来就说不知道，不许编。这条比准确率重要。

**每个功能收尾，固定两个动作。**

一个是独立审查：开个干净的会话，或者派个子会话，只把 diff 给它，让它挑毛病。**不是问它“你确定吗”**——它只会顺着自己刚走过的路再走一遍，错的还是错的。这个项目最容易漏的，恰恰是它看不见的地方：并发、异常路径、跨天。

另一个是让它自己列验收清单，然后照着跑一遍。派活的时候我就说清楚：动手之前先把验收标准列出来，覆盖正常流程、空数据、失败重试，全部通过才算完。终点它先写、我再改——它写漏了我补，它写松了我收紧。

界面这块我会让它自己开浏览器看，而且主动造条件：超长昵称、暗色、窄屏。很多坑代码每行都对，就是渲染出来不对。

**最后上线。**

我把数据库、缓存、服务、网关全塞一台机器的容器里，一条命令起来——手工装环境的东西，换台机器就得再来一遍。前面挂 nginx：静态文件它托管，接口反代过去，跨域顺手就没了。域名加 HTTPS，别用 IP 加端口，微信里打开会被拦。上线前备份、镜像打 tag，回滚就是改个 tag 重启。

**告警这里我特别较真：挂了必须有人喊。**任务停更十天，我还以为一切正常——这是最要命的失败方式，比报错可怕得多。

上线先自己用两天，再给别人看。

**上线之后，我只盯三个数**：登录成功率、识图最慢耗时、诗词接口错误率。每周挑一次翻车，写成一条规则——写规则的过程，其实是逼我想清楚它的边界在哪。

---

这套东西里没有一个技巧是炫技，全是为了同一件事：**让我三个月后还敢改这个项目。**功能砍得掉，地基、契约、检查这三样砍不掉——它们不是功能，是我还能不能继续干的资格。

# 4.你在你这个项目里写了什么契约文件？
我会写四份文档、加两份“代码形态的契约”。原则是**一份文件只回答一个问题**；一份文件想干两件事，两件都干不好。

**一、`CLAUDE.md`——回答“这个项目是什么、哪些地方不能碰”**

一百来行封顶，就四块：怎么跑、目录各管什么、禁区、历史包袱。别写技术教程，别写代码风格（那个交给 lint），也别写成目录索引——索引放 `docs/`。

```markdown
## 命令
pnpm dev / pnpm typecheck / pnpm test src/xxx.test.ts（别跑全量，四分钟）

## 禁区
- 不许新加依赖，要加先问我
- 图片上传必须走 compressImage()，不许直传原图
- auth/ 的双 token 逻辑不许动，改坏了全站掉线

## 历史包袱
- Coze 的 audioUrl 可能是空串，别当它一定有值
- 诗词缓存 key 带日期，不是定时任务刷的，别改回 cron
```

历史包袱这一块最值钱，因为它是**只有我知道、它查不到**的东西。上一版我就是没写，结果它把“看着冗余”的兼容逻辑顺手删了。

**二、`packages/shared/contract.ts`——回答“数据长什么样”**

这份比文档硬，它是类型，编译期就会拦。

```ts
export type Res<T> = { code: 0 | 1; message: string; data: T }

export type RecognizeRes = {
  danger: string | null      // 有危险才有值
  description: string
  audioUrl: string           // 可能是空串，前端要判
}
```

字段名、可选性、空值语义全在这一处。前端拿它写页面，后端拿它写返回，谁想偷偷加字段，类型对不上就报错。

**三、`docs/checklist.md`——回答“什么算合格”**

十条以内，每条都要能判定：

```markdown
- [ ] 新增接口有参数校验
- [ ] 没有空 catch
- [ ] 图片走 compression 工具函数
- [ ] 单文件不超过 400 行
- [ ] 交互有 loading / 失败态 / 空态
```

这不是给工具看的，是给评审用的。工具负责查，清单负责定义查什么。

**四、`docs/adr/`——回答“当时为什么这么定”**

只记那种改起来伤筋动骨、半年后没人看得懂的决策，三篇封顶。比如：

- `0001-token-双令牌.md`：为什么用双 token，为什么刷新失败就跳登录，不搞静默重试；
- `0002-诗词缓存带日期.md`：为什么不靠定时任务保证“一天一首”。

每篇就两段：定了什么、当时为什么。**这种文件不是为了 AI，是为了半年后的我。**

**五、`.env.example`——回答“要配什么”**

每个变量一行注释，说清楚干嘛的、去哪申请。省得它自己编一个变量名，然后我 debug 半天。

**六、两份代码形态的契约（这个不能省）**

- `.claude/settings.json` 里的 hook：改完文件自动跑 lint，报错 `exit 2` 甩回给它；
- `.husky/pre-commit`：提交前跑类型检查和单测。只配一处，别两个都配，否则同一批测试跑两遍。

这两份不是文档，是**跑不掉的约定**。写在文档里的是“建议”，挂在 hook 上的是“必然”。我的标准还是那个：故意写错一个类型，提交必须被拦下来。

**反过来说，什么不写：**

不写“请记得跑测试”（挂 hook）、“用两个空格缩进”（交给 Prettier）、“React 怎么写”（它比我懂）、也不列目录树（那是索引，放 `docs/`）。

这几份文件加起来不到两百行，一个上午能写完。但它省掉的是**后面每一次开新会话都要重新交代一遍**。这笔账怎么算都划算。
